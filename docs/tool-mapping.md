## Merge model (D-04)

File-modifying TeamMate work is delivered in this version through an isolated git worktree and merged back into the leader by the TL Agent. The merge model is **TL autonomous merge + human fallback**: the TL reviews the branch diff and triggers the merge through the explicit `TeamMerge` tool. This **intentionally overrides Phase 5 D-15's no-auto-merge** part — but it is an explicit, auditable TL action, **never a silent background auto-merge**. On a conflict it cannot resolve the TL fails closed (leader rolled back clean, worktree preserved) and can escalate to a human. Auto-deleting workspaces, dropping queued messages, and reconciliation-driven auto-merge all remain prohibited; merge happens only through the `TeamMerge` entry point.

`SendMessage` is explicit only: ordinary assistant text is not a teammate message. `to: "*"` returns `broadcast_unsupported_in_v1`; broadcast delivery is deferred beyond Phase 5. Call `TeamDiagnostics` when the visible inventory, tool status, lifecycle status, durable message/task summary, workspace review state, or caller metadata behavior is unclear.

Lifecycle behavior is backend-dependent start and resume. The default backend reports unsupported execution and never fakes success. Running TeamMate messages are queued for the next turn boundary rather than delivered mid-turn. File-modifying TeamMate work must be isolated or reviewable before it can affect the leader workspace; changed or unverifiable isolated work is preserved as workspace review state such as `needs_review`.

An optional, opt-in real execution backend is available via `CODEX_TEAM_EXECUTION` (with `CODEX_TEAM_EXECUTION_BACKEND`); the default stays the unsupported scaffold and the real backend is never silently auto-enabled. When enabled, `Agent` with a prompt runs an immediate one-shot Codex turn; file-modifying work runs in an isolated git worktree on an independent branch (the worktree is the required isolation boundary — writes never touch the leader tree, and isolation failure blocks the run). On completion the TeamMate notifies the team-lead through the standard message path and lands `idle`; output is never stored (lifecycle-only). If the backend is unavailable, `Agent` persists the records and returns an explicit `execution_backend_unavailable` error with remediation rather than faking a run. OS sandbox flags are best-effort only. `SendMessage`-triggered resume and diff/merge review acceptance are later phases. See [Startup](startup.md#optional-execution-backend-opt-in).

Phase 7 pane mode is optional and backend-dependent. `TeamDiagnostics` reports pane attach/status, lifecycle/run summaries, message delivery counts, task summaries, and workspace review state; it does not report raw prompts, raw message bodies, task text, or full transcript content. The pane transcript experience is terminal scrollback.

Phase 11 connects pane mode to real runs: when pane mode is enabled and a supported terminal backend is available, a real `Agent`-started run automatically creates/attaches a visible tmux/iTerm2 pane and persists its attach metadata (backend type, pane/session/window/socket ids, attach command, availability status) for later diagnostics and resume. The pane is an optional visibility layer **over** the real run — Codex is not run inside the pane, and the overlay never changes the run's status/backend/thread id. If the backend is unavailable or pane creation fails, the run degrades to an `unavailable`/`degraded` pane marker only and durable team/member/run/message/task/event state is untouched (best-effort, purely additive). When a run goes idle or stopped its pane is kept open (D-04); panes accumulate over time as an intentional tradeoff favoring scrollback, and there is no user-facing force-kill/terminate control.

Any user text to a TeamMate must use `SendMessage`, not direct pane shell input. Pane metadata can help attach to a terminal session, but it is not a teammate message transport and it does not add user-facing force kill or terminate controls.

This compatibility layer is not exact Claude runtime parity and is not exact Claude tmux/iTerm2 pane parity. It intentionally avoids claims of true Claude in-process runtime behavior, guaranteed mid-turn injection, hidden Claude CLI args, exact pane parity, or approval-bridge parity.
